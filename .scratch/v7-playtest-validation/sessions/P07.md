## 3. ADVERSARIAL FINDINGS & RETEST ANALYSIS

### 3.1 FINDING-R02.1: Binary Dual-Touch Brake Priority Slams Vehicle into Hard Reverse Across Zero Velocity
- **TAXONOMY**: Vehicle Controls / Physics Friction
- **SEVERITY**: **S2 (Major Friction)**
- **OBSERVED**:
  In [`touch_controls.gd`](file:///Users/bobbyinthelobby/%7Bart/godot/scripts/input/touch_controls.gd#L59-L65):
  ```gdscript
  func _emit_net_throttle() -> void:
      var throttle := 0.0
      if _is_brake_pressed:
          throttle = -1.0
      elif _is_gas_pressed:
          throttle = 1.0
      driving_throttle_updated.emit(throttle)
  ```
  When the player holds Gas with right thumb and taps Brake with left thumb to slow into a sharp corner while travelling at `14.0 m/s`, `_is_brake_pressed` forces `throttle = -1.0`.
  In [`courier_bike.gd`](file:///Users/bobbyinthelobby/%7Bart/godot/scripts/vehicles/courier_bike.gd#L206-L215), when `throttle < 0.0`:
  - `current_speed > 0.1 m/s`: Decelerates at `braking_friction = 12.0 m/s^2`. The bike comes to a dead stop in 1.16 seconds.
  - `current_speed <= 0.1 m/s`: If the player is still holding Brake (or dual-touching Gas + Brake), the bike immediately transitions into reverse acceleration (`-4.0 m/s^2`) up to `max_reverse_speed = -4.0 m/s`.
  Because holding Brake while Gas is held emits raw `-1.0` throttle, players trying to feather the brake to manage cornering speed instead slam to a dead halt and immediately get propelled backward into rear obstacles.
- **PLAYER_REACTION**: *"I was tearing down the alley at top speed, held gas, and tapped brake to take a tight turn. Instead of slowing down smoothly or drifting, the bike slammed on the brakes, stopped dead in 1 second, and started driving BACKWARDS into the wall! Why does holding brake while accelerating force hard reverse?!"*
- **INFERENCE**: Throttle state arbitration treats Brake touch as a binary reverse input command (`-1.0`) rather than a braking/deceleration input while forward velocity is non-zero (`current_speed > 0.0`).
- **RECOMMENDATION**: Modify `courier_bike.gd` drive physics or `touch_controls.gd` throttle emission so dual-touch (Gas + Brake) applies neutral coasting (`throttle = 0.0`) or dedicated braking friction without crossing into negative reverse throttle until Brake is released and re-pressed while stationary.

### 3.2 FINDING-R02.2: Touch Drag-Off Bounding Box Release Traps Gas Input in Infinite Throttle
- **TAXONOMY**: Touch Input / Gesture Soft-Lock
- **SEVERITY**: **S2 (Major Friction)**
- **OBSERVED**:
  In [`touch_controls.gd`](file:///Users/bobbyinthelobby/%7Bart/godot/scripts/input/touch_controls.gd#L95-L102), `gas_button` and `brake_button` bind state updates directly to Godot's `button_down` and `button_up` signals:
  ```gdscript
  gas_button.button_down.connect(func(): _is_gas_pressed = true; _emit_net_throttle())
  gas_button.button_up.connect(func(): _is_gas_pressed = false; _emit_net_throttle())
  ```
  On touch screen devices (and virtual touch drag interactions), if a player presses `gas_button` and slides their thumb outside the button's boundary rect before releasing contact, Godot's `Button` node does not trigger `button_up`.
  As a result, `_is_gas_pressed` remains set to `true`. Even though the player has lifted both hands from the screen, the bike remains trapped at full throttle (`14.0 m/s`), driving endlessly into walls.
- **PLAYER_REACTION**: *"I took my thumb off the gas button to coast into a parking spot, but the bike kept zooming forward at full speed! My character got stuck in full throttle because I swiped slightly off the button box before lifting my thumb!"*
- **INFERENCE**: `BaseButton.button_up` is unreliable for touch input when touch drag events cross control bounds without touch-owner tracking or unhandled touch input monitoring.
- **RECOMMENDATION**: Implement custom `_gui_input` handling or `InputEventScreenTouch` listener on `touch_controls.gd` to clear `_is_gas_pressed` and `_is_brake_pressed` whenever touch phase is `RELEASED` or `CANCELLED`, regardless of pointer screen position.

### 3.4 FINDING-R02.4: Blind Speed Threshold Guessing & 0.6 Dimmed Button Visual Contradiction
- **TAXONOMY**: HUD UI / Visual Affordance Friction
- **SEVERITY**: **S2 (Major Friction)**
- **OBSERVED**:
  In [`scrap_test_block.gd`](file:///Users/bobbyinthelobby/%7Bart/godot/scripts/prototype/scrap_test_block.gd#L160) and [`touch_controls.gd`](file:///Users/bobbyinthelobby/%7Bart/godot/scripts/input/touch_controls.gd#L134-L137):
  ```gdscript
  func set_dismount_button_enabled(available: bool) -> void:
      if dismount_button:
          dismount_button.disabled = false
          dismount_button.modulate = Color(1.0, 1.0, 1.0, 1.0) if available else Color(1.0, 1.0, 1.0, 0.6)
  ```
  Two significant UI friction issues occur:
  1. **Blind Speed Threshold**: The game provides no speedometer (neither numeric m/s nor analog gauge). The dismount threshold is `1.5 m/s` (10.7% of max speed). To the player, rolling at `1.6 m/s` (rejected) looks identical to rolling at `1.4 m/s` (allowed). Players have no visual feedback on whether they are eligible to dismount until they tap and risk a red flash warning.
  2. **Visual Contradiction**: Dimming the button to `0.6` opacity is universally understood in game UI as "disabled / non-interactable". However, `dismount_button.disabled` is set to `false`. When players tap the dimmed button expecting no response, it flashes red and displays a HUD toast warning. The UI visually claims to be disabled, but functionally behaves as active with feedback.
- **PLAYER_REACTION**: *"How fast am I going? The game doesn't show my speed anywhere! I'm coasting super slow and tap dismount, but it flashes red and rejects me. Plus, the button looks greyed out and broken when I ride, but then flashes red when I touch it."*
- **INFERENCE**: Absence of speed visualizer forces trial-and-error tapping. Dimming opacity to 60% mimics a disabled UI button state while keeping touch events enabled.
- **RECOMMENDATION**: Add a subtle speed indicator gauge or speed threshold color tint around the dismount button border (e.g., green border when speed <= 1.5 m/s, yellow border when speed > 1.5 m/s) while keeping opacity at 1.0.

### 3.5 FINDING-R02.5: Unmanaged HUD Toast Timers Cause Premature Label Hiding During Rapid Taps
- **TAXONOMY**: UI State / Timer Race Condition
- **SEVERITY**: **S3 (Minor Defect / Visual Polish)**
- **OBSERVED**:
  In [`touch_controls.gd`](file:///Users/bobbyinthelobby/%7Bart/godot/scripts/input/touch_controls.gd#L139-L152):
  ```gdscript
  func show_dismount_rejection_warning(toast_text: String) -> void:
      ...
      if alert_label:
          show_tension_hud(toast_text)
          get_tree().create_timer(1.2).timeout.connect(func():
              if current_mode == UIMode.VEHICLE_DRIVING and alert_label and alert_label.text == toast_text:
                  hide_tension_hud()
          )
  ```
  When a player rapidly taps the dismount button 3 times in 0.4 seconds while driving at `8.0 m/s`:
  - Tap 1 (t = 0.0s): Spawns Timer 1 (expires t = 1.2s).
  - Tap 2 (t = 0.2s): Spawns Timer 2 (expires t = 1.4s).
  - Tap 3 (t = 0.4s): Spawns Timer 3 (expires t = 1.6s).
  At t = 1.2s, Timer 1 fires. Because `alert_label.text` matches `toast_text`, Timer 1 executes `hide_tension_hud()`. The rejection warning toast vanishes at t = 1.2s — only **0.8 seconds after the player's 3rd tap**, cutting off the message mid-read.
- **PLAYER_REACTION**: *"When I tapped dismount a couple times while riding fast, the red warning message popped up and then instantly vanished before I could even read it!"*
- **INFERENCE**: `create_timer(1.2)` creates anonymous, un-cancelled scene tree timers on every call without tracking or killing previous timer instances.
- **RECOMMENDATION**: Store a `SceneTreeTimer` reference or SceneTreeTween handle `_toast_timer` on `touch_controls.gd`. Cancel/kill existing active tweens/timers before creating a new `1.2s` toast timer.
